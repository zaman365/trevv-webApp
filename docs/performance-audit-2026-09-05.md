# Platform performance audit and improvement plan

Date: 5 September 2026. Source: `841c6f86ecbf60165c1ab48eae4ca69a128658f6`.

## Assessment

The current architecture does too much work to display and maintain a page. Initial application entry waits for organization-wide data, background refresh repeatedly downloads it, and small collaboration responses trigger many database statements. Several interfaces then process and mount complete collections. Sleeping infrastructure and long retry windows add a separate source of unpredictable delay.

The recent repairs were useful but narrow: they stabilized unchanged React contexts, removed redundant server snapshots during client navigation, and eliminated unusable private-route prefetch requests. They did not resolve initial snapshot cost, database amplification, repeated polling, large-list rendering, or dependable background service availability. Passing those regression tests does not establish that the platform is fast.

The recommended program preserves every existing capability. It changes data access, component ownership, scheduling, and verification. A wholesale rewrite or removal of product surfaces is not supported by the evidence.

## Scope and confidence

The audit inspected application routes, live/demo module selection, shared providers, collaboration, rendering, authentication, PostgreSQL repositories/schema, worker scheduling, deployment configuration, telemetry and performance tests. Three parallel source reviews covered frontend navigation, interactions, and backend/data processing. Measurements included an isolated database fixture, compiled Worker assets, a synthetic Calendar algorithm benchmark, public HTTP probes, and aggregate live Cloudflare invocation telemetry.

The live Web reported `web-prefetch-841c6f8`, Worker version `67bad91c-4dd0-46ae-b189-32de2845a7a6`. The API reported source `556d8017cd4a3b6a42cb98761e3f26a574410c37`. Relevant database repositories, schema, API data adapter and worker code are byte-identical between those sources; backend findings therefore apply to the live API despite the different release identities. Web deployments alone do not update the digest-pinned API/worker.

Evidence labels used below:

- **Measured:** observed requests, SQL counts, compiled bytes or isolated CPU execution. Each measurement states its environment.
- **Confirmed:** directly established by source/configuration/history. This proves the mechanism, not its share of a particular user's delay.
- **Hypothesis:** needs a representative query plan, browser trace or production resource measurement.

This is a system-wide architectural audit, not a claim that every interaction has been profiled in production. No representative authenticated mobile HAR, browser long-task trace, production database query plans, or field INP/LCP distributions were available. The live window did not capture an authenticated page switch taking ten seconds. Those gaps are explicit work in the first phase, not grounds for dismissing the reported experience. No product behavior or production configuration was changed during this audit.

**Traffic model, not a production per-user measurement:** let `P=floor(items/100)+1` and `C=max(1,ceil(conversations/100))`, below the pagination failure boundary. Item counts exactly divisible by 100 require an empty completion page. If requests finish inside their intervals, a visible workspace tab makes approximately `12 × (4 + P + C) + 30` API reads/minute before mutations/retries. At <100 items and ≤100 conversations that is about **102/minute**. Messages with one loaded timeline page adds about 39/minute, reaching **141/minute**. Exactly 100 items raises the base model to 114/minute. Retained thread/message pages and additional windows add more. Hidden tabs stop React Query interval polling but retain roughly 30 event calls/minute. Actual rates vary with request duration and browser scheduling.

For scale intuition only: if each sequential item page takes 250 ms, 5,000 items require 51 requests and contribute 12.75 seconds of item pagination to an initial snapshot. That is an explicit assumption, not a measured explanation of the user's ten-second navigation.

## Release safeguards and remaining decisions

Preserve optimistic mutations, idempotency/revision handling, complete history, imports/exports, retention rules, private/team/guest access, offline/draft recovery, modal discoverability, reduced motion and all live/demo routes. Keep private data uncached across identities. Do not extend authorization cache lifetimes to make navigation benchmarks pass. Existing timestamp/context stability, code-only warming and per-workspace denial tests remain useful regression protections.

Deploy additive API/schema capabilities before switching Web consumers; deploy worker improvements with compatible contracts and measured database headroom. Use release-specific telemetry, explicit compatible-version records and a canary where the platform supports it. Roll back the consuming service if errors, access checks, queue age or latency regress; retain compatible additive schema so rollback is possible. Validate actual source/digest/version health from all three services.

The decisions needed for implementation are the always-on hosting budget and engineering allocation. Database plan changes, connection counts, edge placement and broader streaming should follow measurements. Neither a hosting upgrade alone nor another visual loading treatment resolves the confirmed application-level amplification.

Audit deliverables are this plan and the sanitized measurement files. Existing performance documentation and prior regression evidence remain intact; this report adds the unresolved system-wide findings and the work needed to substantiate future speed claims.
