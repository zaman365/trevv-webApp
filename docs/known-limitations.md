# Known limitations

TREVV is currently a fictional-data technical preview. It is intentionally Web-first: the Web/PWA contains the complete interactive demonstration, while Expo and Tauri are foundations rather than feature-parity clients. Do not use real credentials, confidential information, customer data, or the preview as evidence that an external action occurred.

- The hosted polished Web demonstration uses deterministic seeded domain data and browser-local state. In `DEMO_MODE=false`, the founder golden loop plus Teams and Messages are connected to tenant-scoped PostgreSQL repositories. This production-shaped topology exists only in local/CI validation and is not deployed for customers.
- Demo/live mode must be selected explicitly. The hosted preview and example environment use fictional demo mode, where sign-in opens only the labeled sample. In `DEMO_MODE=false`, Web sign-up, one-time email verification, sign-in/out, recovery/reset, explicit session revocation, transactional onboarding, server-owned organization selection, and tenant route guards are real and production-mode tested. That live topology has not been deployed for customers.
- Google Drive exposes configuration seams and a safe demo picker. A production OAuth consent verification, token-encryption key, revocation path, quota policy, and webhook checks are still required.
- The unified Email Inbox is a complete interactive demo using seeded messages and browser-local non-secret account metadata. Live Gmail, Microsoft Graph, Yahoo/AOL OAuth-IMAP, iCloud/Zoho/custom IMAP-SMTP synchronization, encrypted credential storage, provider webhooks, MIME sanitization, attachment persistence, and background reconciliation still require deployment credentials and server infrastructure.
- The closed-alpha scope decision is to include fully implemented Teams and contextual Messages rather than hide them. In undeployed `DEMO_MODE=false`, Team profiles, memberships, Team leads, feature presets, synchronized Team rooms, Workspace/private/direct/external conversations, participants, messages and replies, reactions, request/decision response state, read checkpoints, and retention are durable and authorized. The hosted preview still presents only fictional, browser-local collaboration and sends nothing.
- Team feature presets are product configuration, not authorization. They can shape which relevant tools Team members see, but only current organization membership, Workspace scope, Team membership, conversation participation/visibility, and server policy grant access. Even owners and administrators do not receive implicit access to private, Team, direct, or external message content when they are not participants.
- Live collaboration does not yet support message editing, archiving or pinning conversations, turning a message into work, or binary attachments. Message records can carry bounded JSON metadata, but no upload endpoint accepts file bytes. Object storage is therefore not required by the current alpha topology; private storage, malware scanning, quotas, and signed delivery become mandatory before attachments are enabled.
- Invitation acceptance creates an organization membership. Non-admin roles receive only persisted Portfolio/Workspace grants already assigned by server policy; a complete live scope-management UI is not available yet, so an invited non-admin user can still have no product Workspace to open.
- Import is a fictional dry-run walkthrough and creates no records. Browser-generated downloads contain sample/local data and are not complete permission-checked organization exports.
- Figma, GitHub, and Canva are safe metadata/smart-link previews, not deep sync integrations.
- Authentication/invitation mail uses a configured SMTP adapter in live mode and a private file/memory sink in tests. Product email, direct uploads, malware scanning, signed downloads, push notifications, and provider webhooks remain foundations only. Exactly-once external mail across a process crash still requires a provider-specific delivery handler and idempotency support; the current worker performs internal database effects only.
- Web search filters the fictional browser/demo corpus and does not enforce a server tenant boundary. The live API search is organization- and membership-scoped, but production PostgreSQL full-text/trigram ranking and realistic-volume tuning still require implementation.
- The PostgreSQL worker has three explicit, non-overlapping handlers: Attention, collaboration, and reviewed audit-only acknowledgement for events whose originating transaction is already their complete durable effect. An exhaustive catalog currently maps all 50 emitted outbox event types to exactly one reviewed handler/effect/reason; audit-only is not a catch-all, and a catalog test rejects uncataloged producers. Collaboration owns Team, conversation, message, reaction, read-checkpoint, and scheduled `message.retention_due` events; retention replaces expired message bodies and metadata without deleting their audit identity. Bounded `SKIP LOCKED` leasing, lease-token acknowledgements, jittered exponential retry, terminal dead-letter state, per-handler kill switches, graceful shutdown, queue-age/attempt telemetry, and `/livez`, `/readyz`, and `/metrics` endpoints are implemented. Unknown events remain pending and become a readiness failure when their oldest age reaches the configurable unsupported-event threshold, five minutes by default. External telemetry export, alert thresholds, dead-letter inspection/replay tooling, deployment supervision, and provider delivery remain operational blockers.
- Live Web collaboration receives permission-filtered finite Server-Sent Event batches through the same-origin API proxy and reconnects from a numeric cursor. Authoritative bounded polling continues in parallel, so correctness does not depend on an uninterrupted stream. This is reliable cross-browser invalidation, not a general realtime socket service, delivery receipt system, or presence indicator.
- `compose.staging.yaml` and CI define a production-shaped local topology: standalone Next Web, two load-balanced API processes, PostgreSQL 17, two leased workers, a private file mail sink, and an Nginx edge with self-signed local TLS. The smoke covers authentication/onboarding, one tenant read/write, Team-to-room creation, message persistence, atomic outbox creation, exactly-one-worker handling, and authenticated Web rendering; an upgrade smoke applies the current migrations to a populated previous schema. No remote staging environment was provisioned or deployed, and the local edge/database/mail settings are intentionally unsuitable for public traffic.
- Worker readiness includes recent successful queue telemetry. API `/api/v1/health` remains a liveness response, while `/api/v1/readyz` performs a PostgreSQL round trip; the Web and edge readiness chain fail closed on that result. Remote staging must still validate the full authenticated tenant read/write path before routing traffic.
- PostgreSQL 17 clean migration, populated-schema upgrade, restart, multi-tenant, onboarding, invitation, token replay/expiry, membership removal, founder-loop history/evidence, deterministic Attention, collaboration authorization/durability, concurrency, idempotency, lease recovery, retry/dead-letter, retention, rollback, and audit/outbox coverage run locally/in CI. No production database was accessed or migrated, and the live Web/API/worker/PostgreSQL topology is not deployed.
- Desktop packaging/signing and mobile EAS signing require platform credentials unavailable in source control.
- The 2026-08-29 dependency scan reports four transitive advisories. Two Expo/Metro `image-size` parser findings without patched npm releases are narrowly allowlisted; there are no other high or critical findings. CI continues to block any non-allowlisted high or critical finding.

These limits are kept explicit so the pilot cannot confuse a safe product demonstration with production operational readiness.

The maintainable UI source of truth is `apps/web/lib/product-capabilities.ts`. Promote a capability to `live` only in the same change that adds its authoritative server operation, authorization, durable storage, failure handling, production-mode test, and matching documentation.
