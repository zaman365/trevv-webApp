# Known limitations

TREVV is currently a fictional-data technical preview. It is intentionally Web-first: the Web/PWA contains the complete interactive demonstration, while Expo and Tauri are foundations rather than feature-parity clients. Do not use real credentials, confidential information, customer data, or the preview as evidence that an external action occurred.

- The hosted polished Web demonstration uses deterministic seeded domain data and browser-local state. In `DEMO_MODE=false`, the founder golden loop plus Teams and Messages are connected to tenant-scoped PostgreSQL repositories. This production-shaped topology exists only in local/CI validation and is not deployed for customers.
- Demo/live mode must be selected explicitly. The hosted preview and example environment use fictional demo mode, where sign-in opens only the labeled sample. In `DEMO_MODE=false`, Web sign-up, one-time email verification, sign-in/out, recovery/reset, explicit session revocation, transactional onboarding, server-owned organization selection, and tenant route guards are real and production-mode tested. That live topology has not been deployed for customers.
- The current remote rollout target is the invite-only, fictional-data `$0` alpha at `https://alpha.trevv.de`. Its API and sleeping Worker remain public at `trevv-free-preview-api-zaman365.onrender.com` and `trevv-free-preview-worker-zaman365.onrender.com`. One custom domain included with the current Render Hobby workspace adds no paid resource, but the public sleeping services, expiring backup-free database, report-only CSP, disabled external error reporting, and absent operations stack make this a disposable functional rehearsal—not production-shaped staging, public beta, or GA evidence. Public registration remains disabled, and `trevv.de` is unchanged.
- In undeployed live mode, privacy requests and organization retention overrides are tenant-scoped, versioned, idempotent, durable, and atomic with audit/outbox records. Submission means accepted for human review only: there is no export, erasure, rectification, restriction, provider-revocation, or retention-enforcement processor. These policy records do not control the separate, pre-existing per-message expiry workflow. A user who has lost their final active organization membership currently cannot submit an account-level request, and the lifecycle ledger's direct organization/user/membership foreign keys currently block or cascade with physical deletion rather than preserving a pseudonymized proof record. These are public-beta blockers, not completed privacy controls. The `/privacy` and `/terms` routes are engineering previews with legal review, controller/contact details, DPA, regions, subprocessors, and final retention terms still pending.
- Google Drive exposes configuration seams and a safe demo picker. A production OAuth consent verification, token-encryption key, revocation path, quota policy, and webhook checks are still required.
- The unified Email Inbox is a complete interactive demo using seeded messages and browser-local non-secret account metadata. Live Gmail, Microsoft Graph, Yahoo/AOL OAuth-IMAP, iCloud/Zoho/custom IMAP-SMTP synchronization, encrypted credential storage, provider webhooks, MIME sanitization, attachment persistence, and background reconciliation still require deployment credentials and server infrastructure.
- The closed-alpha scope decision is to include fully implemented Teams and contextual Messages rather than hide them. In undeployed `DEMO_MODE=false`, Team profiles, memberships, Team leads, feature presets, synchronized Team rooms, Workspace/private/direct/external conversations, participants, messages and replies, reactions, request/decision response state, read checkpoints, and retention are durable and authorized. The hosted preview still presents only fictional, browser-local collaboration and sends nothing.
- Team feature presets are product configuration, not authorization. They can shape which relevant tools Team members see, but only current organization membership, Workspace scope, Team membership, conversation participation/visibility, and server policy grant access. Even owners and administrators do not receive implicit access to private, Team, direct, or external message content when they are not participants.
- Live collaboration does not yet support message editing, archiving or pinning conversations, turning a message into work, or binary attachments. Message records can carry bounded JSON metadata, but no upload endpoint accepts file bytes. Object storage is therefore not required by the current alpha topology; private storage, malware scanning, quotas, and signed delivery become mandatory before attachments are enabled.
- Invitation acceptance creates an organization membership. Non-admin roles receive only persisted Portfolio/Workspace grants already assigned by server policy; a complete live scope-management UI is not available yet, so an invited non-admin user can still have no product Workspace to open.
- Import is a fictional dry-run walkthrough and creates no records. Browser-generated downloads contain sample/local data and are not complete permission-checked organization exports.
- Figma, GitHub, and Canva are safe metadata/smart-link previews, not deep sync integrations.
- Authentication/invitation mail uses a configured SMTP adapter in live mode and a private file/memory sink in tests. Product email, direct uploads, malware scanning, signed downloads, push notifications, and provider webhooks remain foundations only. Exactly-once external mail across a process crash still requires a provider-specific delivery handler and idempotency support; the current worker performs internal database effects only.
- Web search filters the fictional browser/demo corpus and does not enforce a server tenant boundary. The live API search is organization- and membership-scoped, but production PostgreSQL full-text/trigram ranking and realistic-volume tuning still require implementation.
- The PostgreSQL worker has three explicit, non-overlapping handlers: Attention, collaboration, and reviewed audit-only acknowledgement for events whose originating transaction is already their complete durable effect. An exhaustive catalog maps every emitted outbox event type to one reviewed handler/effect/reason; audit-only is not a catch-all, and a catalog test rejects uncataloged producers. Collaboration owns Team, conversation, message, reaction, read-checkpoint, and scheduled `message.retention_due` events; retention replaces expired message bodies and metadata without deleting their audit identity. Bounded `SKIP LOCKED` leasing, lease-token acknowledgements, jittered exponential retry, terminal dead-letter state, per-handler kill switches, graceful shutdown, queue-age/attempt metrics, structured content-free logs, and `/livez`, `/readyz`, and `/metrics` endpoints are implemented. Unknown events remain pending and become a readiness failure at the configured age threshold. Dead-letter inspection/redrive, deployment supervision, and provider delivery remain operational blockers.
- Live Web collaboration receives permission-filtered finite Server-Sent Event batches through the same-origin API proxy and reconnects from a numeric cursor. Authoritative bounded polling continues in parallel, so correctness does not depend on an uninterrupted stream. This is reliable cross-browser invalidation, not a general realtime socket service, delivery receipt system, or presence indicator.
- The API and worker produce structured redacted logs and bounded Prometheus metrics; sanitized request IDs propagate through the Web proxy and API. Live production configuration requires a shared PostgreSQL rate limiter whose client keys are HMAC-SHA-256 digests and which fails closed if its store is unavailable. Expired limiter rows are pruned opportunistically during traffic, but no independent scheduled pruning job exists. Web/API security headers and sanitized CSP/client-error report endpoints are implemented; CSP mode is selected at build time and the local topology remains report-only. The current production policy still permits inline scripts, so enforcing mode is not a complete XSS boundary until Next-compatible nonces or hashes replace `unsafe-inline`. The Grafana dashboard and Prometheus rules are repository assets only: no collector, pager, external error tracker, or source-map uploader is provisioned.
- `compose.staging.yaml` and CI define a private production-shaped local topology: standalone Next Web, two load-balanced API processes, PostgreSQL 17, two leased workers, a private file mail sink, and an Nginx edge with self-signed local TLS. The smoke covers authentication/onboarding, one tenant read/write, Team-to-room creation, message persistence, atomic outbox creation, exactly-one-worker handling, and authenticated Web rendering; an upgrade smoke applies the current migrations to a populated previous schema. The API, migration, and worker containers deliberately run with `NODE_ENV=test`, the Web CSP is report-only, and the configuration uses local test credentials. A disposable fictional-data `$0` Render preview may be provisioned for bounded rehearsal; its public sleeping services and expiring, backup-free database are not proof of a production runtime or qualifying remote staging.
- Worker readiness includes recent successful queue telemetry. API `/api/v1/health` remains a liveness response, while `/api/v1/readyz` performs a PostgreSQL round trip; the Web and edge readiness chain fail closed on that result. Remote staging must still validate the full authenticated tenant read/write path before routing traffic.
- PostgreSQL 17 clean migration, populated-schema upgrade, restart, multi-tenant, onboarding, invitation, token replay/expiry, membership removal, founder-loop history/evidence, deterministic Attention, collaboration authorization/durability, concurrency, idempotency, lease recovery, retry/dead-letter, retention, rollback, and audit/outbox coverage run locally/in CI. No production/customer database is authorized or migrated, and no qualifying production-shaped Web/API/worker/PostgreSQL topology is deployed; a disposable fictional-data preview does not change those gates.
- Desktop packaging/signing and mobile EAS signing require platform credentials unavailable in source control.
- The 2026-09-04 dependency scan reports five advisories: two high and three moderate. The two high findings are `image-size` parser denial-of-service issues (`GHSA-w3rx-r6r6-pgpr`, `GHSA-5p2g-fcmc-qvqq`) with no patched npm release, reachable only through the Expo/Metro toolchain under `apps/mobile` and therefore outside the Web/PWA release scope. `scripts/audit.mjs` narrowly allowlists exactly those two and fails closed if their module name or Expo/Metro-only paths change. The three moderate findings are build-time dependencies. CI continues to block any other high or critical finding.

These limits are kept explicit so the pilot cannot confuse a safe product demonstration with production operational readiness.

**Phase 5 / public beta: NO-GO.** A reviewed legal/privacy package, account-level DSAR access after membership loss, a deletion-safe lifecycle ledger and real privacy-effect processor, managed backup/restore evidence, remote production-mode staging, active telemetry collection/paging/error reporting with source maps, a nonce/hash CSP without `unsafe-inline`, dead-letter redrive, scheduled operational cleanup, and pilot/pricing evidence are still missing. No integration, AI external effect, file service, or billing capability is approved or enabled.

The maintainable UI source of truth is `apps/web/lib/product-capabilities.ts`. Promote a capability to `live` only in the same change that adds its authoritative server operation, authorization, durable storage, failure handling, production-mode test, and matching documentation.
